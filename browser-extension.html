Browser Extension Layer

Native messaging bridge, pre-browser registration, webRequest interception  ·  companion to cowork.exponential-systems.net  ·  2026-01

The main Cowork architecture page documents this surface at the macOS level. This page provides the full technical characterization of the signal path, the pre-installation registration mechanism, and the relationship to Genesis.Genie — the clean-room reconstruction of the native host binary.

Native Messaging Host Registration

Claude Desktop silently installs a Native Messaging host manifest (com.anthropic.claude_browser_extension.json) into the configuration directories of Chromium-based browsers on the host — Chrome, Edge, Brave, Arc, Vivaldi, Opera, and others — including browsers not yet installed at the time of registration. No disclosure is made during installation. No consent is requested at install time or when a browser subsequently finds the pre-registered manifest.

Independent discovery of this surface occurred in January 2026. Public coverage appeared approximately three months later.

chrome-native-host

The registered native host is chrome-native-host, a Rust binary (2.1 MB, universal x86_64+arm64 on macOS) that runs outside the browser sandbox at user privilege. It is the only binary the extension can communicate with via the native messaging protocol, and its execution is authorized by the pre-registered manifest without additional prompting.

Signal Path

Browser → MCP
→Chrome extension (sandboxed JS)
→chrome.runtime.connectNative() → chrome-native-host — Rust, outside browser sandbox, user privilege
→Unix domain socket → Claude Desktop main process
→WebSocket bridge → MCP servers

webRequest Operates Before TLS

The webRequest listener on api.anthropic.com intercepts at the browser network layer — before the request is encrypted for transport. This is structurally different from the CCR proxy (which operates at the container TLS boundary) and the sdk-daemon proxy (which operates inside the VM at TLS). The browser extension layer sees plaintext request content before any TLS layer can intercept the ciphertext. In a complete request path through all three layers, this is the first point of interception.

Genie: Clean-Room Reconstruction

Genesis.Genie is a clean-room reconstruction of the chrome-native-host native host binary, built from behavioral observation of the native messaging protocol and the capabilities exposed by the binary. It is not a fork or modification of the original binary.

The reconstruction produced:

  • Genesis.Genie.Bridge — managed bridge for the native messaging protocol
  • Genesis.Genie.NativeHost — host-side implementation (C#) of the native host capability surface
  • Genesis.Genie.Bridge.Tests and Genesis.Genie.NativeHost.Tests — conformance test suites

The four assemblies reside on the development machine and have not been committed to the public monorepo.

Same Capability, Different Trust Context The debugger permission in the extension and Genie's CDP access capability reach the same Chrome DevTools Protocol surface — full tab state, network, storage. The extension operates from inside the browser's extension sandbox with manifest-declared permissions. Genie operates from the desktop level, outside the browser entirely. Two paths to the same capability, from different trust contexts, with different user visibility.
