Capability Composition

Aggregate interoperability surface — all layers  ·  companion to cowork.exponential-systems.net  ·  2026

This page synthesizes the individual capability surfaces documented across the companion pages into a single view of the composed ecosystem. Each layer is independent — different mechanisms, different trust boundaries, different operators. Individually, each has been characterized. Composed, they represent the complete interoperability surface that operates on API traffic, session content, and the host environment.

What a Single API Call Traverses

For a browser-originated Claude API call from a machine with Claude Desktop, the active Cowork VM, and the browser extension installed:

Browser → api.anthropic.com: Full Path
→User types in Claude UI (browser)
→ BrowserExtension webRequest intercepts at network layer  — plaintext, before TLS
→Request encrypted, leaves browser → claude.exe → container boundary
→ CCREgress Gateway intercepts at container TLS boundary  — decrypts, inspects, re-encrypts
→Re-encrypted request forwarded into VM
→ SDKsdk-daemon proxy intercepts at VM TLS layer  — decrypts, inspects, re-encrypts
→Forwarded to api.anthropic.com

Three interception points. The user has visibility into none of them — each operates transparently below the application layer and each CA is trusted by its respective runtime. The user's TLS library confirms "certificate verify ok" at every step.

Directional Blind Spot Matrix

Each layer intercepts a specific segment. Modifications made at one layer are not visible to layers that have already processed the same request:

If this layer modifies outbound Browser layer sees it? CCR sees it? sdk-daemon sees it? Anthropic API sees it?
Browser extension modifies request — Yes Yes Yes
CCR modifies request No — already processed — Yes Yes
SDK sdk-daemon modifies request No No — already processed — Yes

On the inbound path (response), the order reverses: sdk-daemon processes the response first, then CCR, then the browser extension. A modification by sdk-daemon on the inbound response is invisible to CCR and to the browser layer.

Orthogonal Surfaces: Not Intercept Points

Two surfaces operate orthogonally to the API intercept chain — they do not sit in the request path but interact with the environment:

sdk-daemon Updater: Write-Back Surface

The updater detects hash drift in monitored files and writes back through the virtiofs guest-to-host mount. The write surface is not bounded to a single directory: any path accessible through the virtiofs mount can be monitored and restored. The evaluator's source code, its test suite, and its repair pathway are potentially within this write surface — the structural observation documented at cowork.exponential-systems.net.

subscribeEvents: Exfiltration Surface

The unauthenticated VM event stream gives any local process — including MCP servers — real-time access to everything the VM produces. This is not an intercept of the API request; it is a parallel channel that receives the AI response, tool output, and file contents as they are produced inside the VM, without requiring any authentication. Documented in full at subscribeevents.

WDAG Bridge: Independent Boundary

The Win32/WDAG bridge (wdag-bridge) operates at a structurally different boundary from all three TLS interception layers. It uses HvSocket over VMBus rather than TLS, targets the Win32 and WDAG Hyper-V boundary rather than the network path, and was found pre-deployed in the environment rather than installed as a user-visible component. It is not in the API call path and does not operate on network traffic. Its capability surface — UIAutomation, message injection, cross-VM-boundary COM launch — is independent of and not visible to the other layers.

Conversation Content: Record Integrity

The filtering of 21 conversations from the API and exports (conversation-filter) is not a capability that operates on API traffic. It is a capability that operates on the record — what the account holder can see and export vs. what exists on Anthropic's servers. Its significance in the composed picture: the evidence chain for the other capabilities documented here is itself potentially subject to this filtering mechanism.

Aggregate Effect on API Traffic Integrity

A single Claude API call from a user may be observed, logged, or modified at three independent interception points (browser, CCR, sdk-daemon) before reaching the Anthropic API. Each point is operated by a different mechanism. No single point has visibility into the full chain. The user has visibility into none of the three. Standard TLS verification confirms "ok" at each intercept because each intercepting CA is trusted by the runtime at that layer. The user's reasonable expectation — that their API call was encrypted end-to-end to the Anthropic endpoint — is not satisfied by the architecture as documented.

Each individual surface page contains its own primary evidence and sourcing. The composition described here follows from those individually documented surfaces — it is a structural characterization, not an allegation about any specific use of these capabilities.
